Stella's Dark Sky

July 2026

The Arkansas Natural Sky Association (ANSA) had a quiz they asked their members and visitors on the causes and effects of light pollution that they wanted to be spruced up. I, along with the Emerging Analytics Center (EAC), prompted them to make the quiz a game so that younger learners could enjoy the experience more, and thus Stella’s Dark Sky was started. The goal was to make a short game with an improved version of their quiz at the end. The game needed to cover light pollution and its effects, but in a way that children could understand and enjoy.

To create Stella’s Dark Sky I used Unity Game Engine, for development of the game. Sound effects created for the game were made using Audacity. The game’s source code was handled through Sourcetree/bitbucket. Project management was maintained using Jira for task management and Confluence for documentation.

The completed game is a 2D point and click adventure style game, where you go around finding parts of street lamps, learn about light pollution and fix the street lights to be better lighting for the environment. When the player completes the lights, they are then given the ANSA quiz on light pollution.

In development of the game, handling the various states of the lights proved to me a consistent issue. When one thing was fixed, another would break, and this became a regular fix. In the end, the lights turned out well, but refactoring became regular as certain systems needed to change to fit new needs.

This project taught me a lot about the development life cycle, going from prototype to full version proved quite a task for such a small game. This project was one that I led, and had a lot of creative control over. While I am proud of all that I was able to accomplish with the project, I certainly see a lot of room for growth in a game like this. This project really wrapped all of the learning I had done with the EAC into a nice bow, learning not only about development and programming, but project management, application design, audio engineering, game testing, bug fixing, and more.

Stella’s Dark Sky was built for the web and placed on the ANSA website for users to play and enjoy. While no data has been collected to show the effectiveness of the game and its spreading awareness of light pollution, I think the project was still a major success in what we set out to make. It encapsulates the ideas of light pollution, and overall is a great experience for young astronomers.

Unity Backup Generator

June 2026

The Unity Backup Generator script project came from a need to backup Unity source files as I would occasionally forget to backup my files when working on a project, relying only on my Git repositories. This script’s goal was to smartly make a copy of my projects folder and back them up to a network storage device that was installed in the Emerging Analytics Center’s lab. The script needed to make these copies in a way that removed regenerative files (files that are created by Unity automatically) to make the size and speed of the copy faster.

To create this script, I used Powershell to make the script, Window’s Task Scheduler to automate the script’s task(s), and GitHub to maintain source code. My IDE of choice for creating the script was Visual Studio Code.

The resulting script allows the user to designate a source and destination folder, where the script will run, create a new folder in the destination, create a log called “{todays-date}.txt” where it will include all of the steps taken in the copy process. The script will begin to copy the contents of the source folder, into the new folder created at the destination. The script will skip certain file types and folder names as Unity folders hold regenerative files, for example the Library folder, and when complete will mark the start and end time in the log, telling the user that the copy process has been completed with statistics about the copy process.

During development of this script, I found that copying via robocopy can take quite a bit of time. While I did not test the speed difference between drag and drop copying versus my scripts copy method, however, the automation does help save time as the backup is one less thing to worry about.

This project taught me a new command in Powershell, and taught me more about how I can utilize Powershell to automate routine tasks. I learned a lot about robocopy and the many different ways I can make smart copies of folders to avoid unnecessary copying.

The resulting script is a helpful back-up generation script that smartly copies Unity project folders and packages them nicely into a destination folder with a log to provide further context to the copy process should an issue occur. Having been using this script since I made it, I have found it quite helpful for my day to day work, as I don’t have to constantly worry about my project files being backed up.

Future works on this script could include making the script smarter, having it target only Unity project files in case something accidently falls into the projects folder by mistake. Removing old backups after a set period of time. Additionally, zipping backups to try and reduce storage needed for backups.

Ultimately, the Unity Backup Generator script has been a very helpful tool and resource, as it allows for users to worry less about backing up files, and makes development less risky as you have automatic backups to fall back to should new changes cause an issue.

AutoMinimize

June 2026

The AutoMinimize powershell script came from a need for the CAVE, a VR environment housed in the Emerging Analytics Center’s (EAC) lab. As the CAVE is several machines connected together and synced, there are daemon processes that run on each of the machines to sync them. The daemon that runs to sync the CAVE nodes has a small window that turns on with the CAVE nodes, and was something you had to manually minimize. The script was made to remove the need to manually minimize the process window.

To create the AutoMinimize script, I used Windows Powershell to create the script, and used Visual Studio Code as my IDE of choice for this program. To fully automate the script I used Windows’ Task Scheduler to automatically run the powershell script when the computer(s) start up. My source code was maintained using GitHub.

The finalized Powershell script allows the user to target a specific process and when run, will minimize the selected process should the script find a process by the inputted name. The script is designed with web browsers in mind, as most modern web browsers have many background processes running alongside the visual process users typically interact with. This script will target what should be the visible or main process to then minimize.

While creating this Powershell script, I found that the ability to minimize a process is held in a .dll file named “user32.dll” I also found out that many of these .dll files are written in C++ but have a C# translator specifically to interface with programs like Powershell to make it easier for automation.

This project taught me a lot about Powershell and making automation scripts. I learned about writing Powershell scripts, how to automate those scripts using Task Scheduler, how to find/add functionalities to Powershell scripts, and how Powershell and C# interface with one another.

The resulting script is a small but helpful script for minimizing a target process. This script has sped up preparation time for CAVE demonstrations making it simpler for CAVE operators. The success of this project led me to work on more Powershell automation scripts to automate things around the lab and in my work environments.

FBXViewer

June 2026

The FBXViewer CAVE application is an expansion on the CAVE Oil Terrain application, focusing on making a CAVE application that allows users to load, view and manipulate FBX models on the fly. The FBXViewer attempts to remove the need of rebuilding project files to the CAVE.

The FBXViewer application was developed using Unity Game Engine and MiddleVR’s Unity packages to create the CAVE application. The source code was maintained using GitHub and project management was handled through Jira. The development methodology for this project focused on making the application work on PC before porting the project over to the CAVE, so we could focus on building the on-the-fly FBX loading.

When development of the project was completed, the FBXViewer was capable of processing an FBX file, transforming FBX information into a JSON and a GLB file. Model files can then be added into the CAVE application to be interacted with by the user. When processing a model, the application will center the model to ensure that it is roughly centered. If the offsets are not quite where a user is wanting, they can go into the JSON file and change the transforms, scales and rotations of the model to be where and how they want.

During development, we had to toy with different file conversion methods for on the fly spawning of the FBX models. We ended up using GLBs as they load after when used in the context of Unity’s streaming assets folder, where files can be added at run-time for the application to then load. We found during development that while FBX’s are a native 3D model type for Unity, the file type is not recognized by Unity when placed in the streaming assets folder, which caused issues at first, but the GLB conversion was the solution to that problem.

Development of the FBXViewer taught me a lot about generating JSON files, using recursive functions in large sets of data, and developing functionalities that cross platforms. This project also helped cement my knowledge of Git and project management, working with merge conflicts and ways of handling branches.

The project was very successful in what we aimed to do, however it required further future work in order to be the fully realized application we had in mind. In the state that we left the project, FBX models are able to be generated, and placed into the CAVE application on the fly using GLB files. Models load in, and are able to be scaled, moved, rotated and swapped out. However, some models do not initially spawn correctly, due to offsets when made in the 3D modeling softwares, and thus require tweaking the JSONs occasionally. This can be remedied by an in-application method of saving a model’s current offsets when spawned into the CAVE application. Additionally, while the models can be spawned in as a series of parts, they do not currently have a method of selecting specific regions. Selecting regions would allow users to take models apart, possibly disable certain parts of the model, and manipulate the parts of the model they want to change.

CAVE Insects

October 2025

The Emerging Analytics Center (EAC) had an AR project titled Insects AR which was a series of cards that included bug information that, when paired with the app, would show 3D models of the bugs they represented and give information about the bugs. Originally made in collaboration with a local pest company, we adapted the AR application into a CAVE application in anticipation for the natural museum being established at the University of Arkansas at Little Rock’s campus. The goal was to create a museum-like setting for viewing the same bug information and facts as the AR version, but utilizing the space of the CAVE.

To create CAVE Insects I utilized Unity Game Engine and MiddleVR’s Unity packages to create the scene and integrate it with the CAVE. Project’s source code was maintained with Sourcetree/bitbucket and project management was handled through Jira. In creating this project, I adapted similar concepts and tools as my VR Summer Camp material.

This educational application proved to be educational for insects, great for viewing bug models, information and animations in a large environment. The project became a good proof of concept for a virtualized museum exhibit, using picture frames as diegetic user interfaces. The application also includes sound effects and ambience, auto rotate feature, and UX settings for changing audio volume and hiding UI elements.

During development of the CAVE Insects app, figuring out how to best spawn the models proved difficult as many of the models had a variety of sizes. Using Unity’s scriptable objects, I was able to easily set up basic templates for bugs with their size offsets to spawn them with the same relative size. Additionally, making sure the multiple renderers would sync correctly proved challenging at first, but with the many useful tools in MiddleVR, this was not a terribly complicated process.

While developing this project, I learned more about MiddleVR and the multiple settings and scripts they offer for multi-cluster rendering, and I learned more about scriptable objects and how best to use them. While much of this project was redoing things I had done before, this project helped to solidify my learning from other projects and to make similar systems I had made in previous projects better.

The project ended up rather successfully as a good proof of concept for future works for the lab. Many of the tools and scripts used to create this project built on the principles learned in many previous projects I had worked on. Future works of this project would be expanding the variety of bugs shown in the exhibit, more information and animations of the bugs, and voice-narrated tour(s) of various bugs and their environments.

VR Summer Camp - Spaceship Repair

June 2024 - July 2025

Every summer the Emerging Analytics Center (EAC) holds a VR summer camp, where we teach 5th - 12th graders how to develop on Oculus headsets using Unity Game Engine. For these camps, every year since I joined I have participated in developing and teaching learning materials to the summer camp students. The material I have made and revised every year was for a short spaceship repair game inspired by the car mechanic section of Job Simulator.

Creating the material and subsequently a small test game, I used Unity Game Engine for primary development, and focused my development for Oculus Quest headsets. Our design philosophy for the VR summer camp was to create bite size prefabs and packages for students to learn the basics of Unity with, making these segments as close to drag and drop as possible, while also having the many features of Unity. The source code was maintained using Sourcetree/Bitbucket and project managed using Jira.

The final project ended with success with additions every year, students were given my learning packages and many students created some amazing variations of the spaceship repair game using the tools created for them. It was observed that most students who utilized my packages struggled with using certain tools. Odd sized models caused the greatest issues with performance and ruined certain interactions when active.

In future works of the VR Summer camp material, I would focus on modularizing the various parts further, I would add more feedback and functionality to the various tools that are used to repair ships, and ideally, I would make the ships breakable, or allow for the user to change parts of the ship out, rather than focusing on repairing small issues on a ship.

The project(s) were great learning experiences for both the students and myself, and I had a lot of fun teaching Unity development. During the development phase of the project(s) I learned a lot about VR development and documentation as I worked on designing the course material alongside developing my test game. I learned a lot about refactoring and modularization as I worked to make the tools for the spaceship game, without forcing the tools to solely be used for that purpose. I honed skills in C# and Unity generally as I worked to make the scripts drag and drop, and making the inspector interface for my scripts clean and understandable.

Teaching the course, I learned how to explain Unity to new users, not only enforcing what I had already learned from Unity, but helped me learn things about Unity I never had known beforehand. The students helped to inform the changes for the next version of the camp material, and have taught me how to best take user feedback and apply it to future updates.

Overall, the VR Summer Camps and the project I had gotten out of the experiences were rather successful. I got to teach students how to use Unity, they taught me how to be a better developer, and I learned a lot about VR development, code collaborations, documentation, and teaching others about custom tools. These projects helped to not only teach for the summers I was involved, but also helped to become a baseline for future summer camps in the future.

CAVEViewer

May 2025

The CAVEViewer was a series of projects focused on turning the Emerging Analytics Center’s (EAC) 360 tour projects into CAVE applications and creating a template for future tour ports to the CAVE. This project specifically targeted making a CAVE tour of the Trojan Way and Alumni Brick Path, walkways at the University of Arkansas at Little Rock, which at the time was recently renovated.

To make the application, I used Unity Game Engine, and MiddleVR packages to handle the cluster rendering for the CAVE. I managed the project using Jira, and used Sourcetree/Bitbucket for source control. A Insta360Pro camera was used to capture the Trojan Way and Alumni pathways.

The final project included a Google Maps like interaction scheme, where users could direct themselves up and down the pathway using arrow buttons on the floor. A map of the pathway that tracks the user’s position and teleports to selected sections of the pathway. The application also includes features such as ambient audio, auto rotate and a hide UI option.

During and after development of the CAVEViewer, the directional buttons were often an issue, as the multi-cluster renderer packages of MiddleVR did not work nicely with spawning UI elements to create the Google maps-like interactions. I instead had to constantly hide and retool existing buttons to work with new environments that the user would move too. This created quite a few issues during development, where I needed to constantly go back and make minor tweaks to button placements and store their positions.

In future works, I would ideally find a way of making graphing tools like Digital Salmon’s Complete 360 packages, which allow for developers to make marks on the panoramic images to dictate where a UI element would be placed. However, for the scope of the project, this was more work than what was needed at the time, and would have been a significant time sink. Additionally, while I did keep many features as modular as I could, there came a time where some features needed to be tied to other features to ensure they synced up, which in future works would not be required.

Working on this project, and the creation of the template, I learned a lot about setting up modular features, and how to best set-up scriptable objects within Unity projects. I learned a lot about MiddleVR and multi-cluster rendering generally, and learned a lot about good UI practices within 3D environments.

This project resulted in a CAVEViewer template being established for future 360 tour projects. The creation of two CAVE applications used for promoting features of the university's campus, as well as standardizing floor buttons within future EAC projects.

Chemical Beach

October 2024

In partnership with the Department of Defenses’ outreach program Starbase, and the Forge Institute, the Emerging Analytics Center (EAC) was asked to create a series of applications and set up a version of our Immersive Corner, a VR environment. In this I was tasked with making a VR scavenger hunt game, meant to be used as an educational piece to help teach chemistry topics based on another game they have called “Happy Atoms”

To create this application, I utilized Unity Game Engine and maintained project management through Jira, maintained code through Sourcetree and Bitbucket and created project documentation using Confluence. Throughout the development of Chemical Beach, the Agile workflow methodology was utilized.

When Chemical Beach’s development was completed, the game included various items to find, with chemistry facts included, allowing the user to interact with the molecule. A stylized cloud generator, a directional arrow to make the scavenger hunt easier for younger users, and a simple player controller with controls for both keyboard/mouse and controller set-ups.

In developing Chemical Beach, figuring out good cloud generation proved to be quite a challenge, as early versions of shaders were used, and particle effects had a variety of issues, from being inefficient performatively, to not generating enough clouds. In the end, using a simple cloud png, and layering them on top of each other, with a variable spin, size and texture noise created an ideal generation, which was commented as being “Miyazaki-like.”

During this project, I learned a lot about developing for non-standard platforms, as we had to create functionalities for a game that existed on more than one screen at a time. Where at first I created methods for a dual monitor set-up, then later retrofitted functionalities for a Nvidia mosaic mode setting. This project also taught me more about particle systems when creating the cloud generator. Chemical Beach has also taught me a lot about level and environment design, and how to place objects in an environment in an effective manner, and create a memorable scene for users.

This project also taught me a lot about project management, as I worked on managing the Jira board and tasks for developers and artists. Learning not only how to develop applications but also manage people in an Agile workflow.

The resulting project was a fun scavenger hunt, utilizing the immersive corner’s VR setting to its advantage, creating a fun way of teaching chemistry topics to young learners. This project was one of the first major projects I did most of the management on, helping to build my skills not only in development, but also organizing large projects among several other project teammates.

Oil Terrain

March 2024

Upon first joining the Emerging Analytics Center (EAC) my first major project was to recreate and adapt an older project called GeoTerrain, a data visualizer built for Microsoft’s HoloLens. The original application was made to view a specific terrain model based on data seen in ArcGIS. Together with another student, our goal was to bring the same concept to a tablet, the CAVE and the web. In planning and developing we asked ourselves important questions, such as: What are the common controls for this application across each platform? What will need to change for each port? How can we make each of these experiences transferable to each other?

In developing Oil Terrain, we utilized Unity Game Engine for each of the ports of this application, we utilized Vuforia packages to create and find image targets for the application to use as an anchor for the AR port, and we utilized MiddleVR for our CAVE port. Project management was maintained through Jira, code through Sourcetree and Bitbucket and project documentation was made using Confluence.

What resulted was three applications each tailored to their respective platform. In our AR version of OilTerrain, we made it simple for users to lock onto an image target, where they can view the Terrain physically in the world. We made simple UI elements to manipulate the terrain without needing to move around the object.

In our CAVE port, we made it possible to view the Terrain data as if the user were physically there. Allowing for users to “stand on the shoulders of giants” or view the data like a diorama. We utilized the CAVE’s immersive nature to allow for better collaborative settings, and allowed for easier viewing of the terrain data utilizing a Vive wand for controls. We implemented many of the same functionalities as the AR version, however, added functionalities to cater to the new ways of interacting with the terrain that the CAVE offered, such as grabbing the terrain, and spinning it with the wand.

Finally, we took everything we had built up to that point, and ported it to the web, where you can interact with the oil terrain the same way as you could in the AR version, but without the image target being required. Utilizing the same functionalities, but with less headache of needing a tablet and a printed out version of the image target, or needing the CAVE.

During the development of these projects, we learned a lot about the struggles of porting applications to various platforms, how to develop new features for various platform types and honed our knowledge of collaborating in Unity development using Sourcetree and Bitbucket. Making new features, particularly for the CAVE helped us learn more about developing for VR applications and building for the web helped us learn to optimize our work to ensure our application fit within a certain file size.

While Unity was not new to us, MiddleVR, and Vuforia were new and we learned a lot about parsing documentation, and creating our own internal documentation regarding ways of integrating tools like MiddleVR into specialized environments like the CAVE. These projects also got us more comfortable with Unity tools and builds as we worked on making several different versions of the same application, but on different platforms. This project also introduced shaders graphs to me, as we created some bounding boxes for the CAVE Oil Terrain to keep users from accidentally moving the model or themselves out of view.

The result of these applications became a primary demonstration pieces for future clients. Showcased several times to industry professionals, these applications became working proof of concepts for future projects in the CAVE, such as CAVE Insects, CAVEViewer and FBXViewer.
